# Daemon-owned mission execution

Engineering slice only. Real provider profiles remain refused. No service is
installed or started by a client, and no live-provider readiness is asserted.

## Operator and client contracts

The operator starts the existing factoryd with its trusted role-policy file.
The owner holds a canonical root/device/inode identity, process identity,
generation and private Unix endpoint. Readiness follows durable reconciliation.
Production factoryd --once also acquires ownership and processes admitted work.

Clients attach to an already-created mission:

```sh
factoryv2 run --root ROOT --mission MISSION --request-id REQUEST --max-steps 1
factoryv2 result --root ROOT --request-id REQUEST
```

--wait observes for at most 60 seconds, then returns the current request.
Waiting or disconnecting does not cancel execution. Each RPC has a two-second
socket timeout and a one-MiB response limit; the server accepts at most 64 KiB.
Request IDs and mission IDs are bounded ASCII identifiers (128 characters);
max-steps is an integer from 1 through 100. No role policy, engine, environment,
credential, root grant or tool grant is accepted in a mission RPC.

Repeated request key and identical mission/step payload returns the same
durable request. Changed payload conflicts. A second unfinished or quarantined
request for the same mission is refused. Finished bounded execution does not
mean the objective succeeded: the returned mission state and role-attempt
records are authoritative; objectiveCompleted is never inferred from RPC
acceptance or a successful controller iteration. Results are keyed by request,
not by latest mission state.

Goal enqueue/status remain available. Enqueue alone does not execute a mission;
production daemon startup no longer drains arbitrary queued missions/goals.
Direct controller and daemon.runOnce calls are local library interfaces.
--local-test explicitly retains the old CLI test consumer, with no durability
claim, never as fallback and never on a root with an owner record.

## Interruption and cleanup

Admission and execution-start markers are fsynced to the existing event journal.
An admitted but never-started request can be picked up by a replacement owner.
A start marker without a persisted outcome is quarantined, even when a role
appears settled. Cleanup uncertainty similarly prevents a new request for that
mission. No executing worker is adopted and no old PID is signalled.

Linux stale-owner recovery requires evidence that the recorded process is
absent or has a different boot/start identity. A stale socket additionally must
match the recorded inode and refuse a connection. Missing/malformed ownership,
an unknown socket, a damaged journal or an abandoned acquisition guard fails
closed. An operator must reconcile these states; there is no automatic force
recovery. Non-Linux recovery is deliberately conservative.

The acquisition guard serializes publication/recovery. An owner generation and
socket identity are checked before execution and before server close. Clean
shutdown removes the endpoint before relinquishing the owner record. Uncertain
endpoint cleanup retains the fence rather than claiming success.

The Linux exec gate additionally requires an explicit permit on a separate
owner pipe. EOF before permission refuses the provider, including when bwrap's
setup barrier wakes on EOF. The fixed launcher executable and script hashes
are included in the effective policy digest and rechecked before spawn.
This addresses the reproduced pre-permit interruption; it does not certify
every possible timing after a permit has been issued.
