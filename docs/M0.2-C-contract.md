# M0.2-C controller role contract

Scope: mission controller integration only. R1/R2 remain accepted. All real
provider profiles remain `ISOLATION_UNSUPPORTED` before generating spawn. This
does not close provider auth/config/egress, whole-tree containment or the host
incident, and does not authorize M0.3/G12, JARVIS, merge or deployment.

## Trusted configuration

`createController` and `createDaemon` accept exactly one explicit policy source:
`rolePolicies: { worker: adapterConfig, reviewer: adapterConfig }`, or
`rolePoliciesPath` naming operator JSON of that same shape. `factoryv2 goal/run`
and `factoryd [--once]` accept `--role-policies <file>`. There is no inferred
profile from engine, prompt, environment, default channel or mission result.
The existing engine flag alone cannot authorize a controller worker. No production
configuration was installed; launchd provisioning is outside this slice.

Each role uses the existing adapter configuration/schema: explicit engine,
command/executable pin, workerPolicy auth/config declaration, readRoots,
writeRoots, stateRoot, tools/denials, output/cleanup limits and budgets. Policy
files must be regular, not group/world writable, and outside the configured
worker write grants. Direct objects are trusted operator API arguments. Inputs
are snapshotted/frozen; daemon reconstruction intentionally reloads an explicit
file and subjects any changed policy to the same session compatibility checks.

Both roles compile before either adapter is constructed or run. Missing roles,
unsupported real profiles or invalid grants are typed refusals with no generating
spawn, no review success and no repair churn. CLI run exits nonzero on a typed
controller refusal. Goal admission without a policy may queue intent, not run it.

Worker business roots are the intersection of explicit trusted grants and the
exact controller-owned `root/worktrees/<mission-id>` canonical path. Reviewer
business writes must be empty in configuration and requests. Reviewer tools
cannot exceed its own configured availability. Runtime exceptions cannot expose
business data or either role's private state. R1/R2 exact tool denials, root
validation and unsupported-combination refusals are reused unchanged.

`mission.roleRequests.worker/reviewer` may only contain existing narrowing
options: allowedTools, disallowedTools, readRoots, writeRoots, limits, timeoutMs,
maxTurns. Requests cannot select engine, executable, env, auth, state/runtime
roots, model, identity or resume digest. Reserved override fields and unsafe
mission IDs refuse. Results are never merged into policy or session authority.
The existing controller verification/release state machine is not redesigned.

Each private state namespace is a SHA-256 of canonical controller root,
mission ID and role under that role's trusted private (0700) state base. Bases
may be shared; namespaces and digest-specific HOME/config directories cannot be.
`controllerBinding: { controllerRoot, missionId, role }` is included in the
immutable effective profile. Existing channel profile shapes remain unchanged.

## Durable sessions

One append-only `mission.role.session` event atomically records:

```json
{
  "missionId": "mission-example",
  "role": "worker",
  "record": {
    "version": 1,
    "missionId": "mission-example",
    "role": "worker",
    "engine": "claude",
    "sessionId": "provider-session-or-null",
    "profileDigest": "effective-policy-sha256-or-null-on-reset",
    "attemptId": "owned-controller-attempt-uuid",
    "status": "running|settled|uncertain",
    "terminalCause": "EXIT-or-typed-cause-or-null",
    "externalEffects": "NONE_DECLARED|UNKNOWN"
  }
}
```

The journal materializes `mission.roleSessions[role]` and legacy display aliases
workerThreadId/reviewerThreadId from this same event. A running record is fsynced
before `thread.run`, even before a provider session ID exists. ID callbacks update
the complete record with the already-compiled digest; bare IDs never authorize
new resume. Returned identity/profile/terminal metadata must match. A peer-role
ID collision blocks review and requests cancellation, never repair or approval.

Fresh adapter/controller instances resume only a settled, version/mission/role/
engine/digest-compatible record. Settled changed profiles or missing provider
sessions reset only the affected role and start fresh. Legacy bare IDs require
a matching successful EXIT receipt after the last recorded role activity;
otherwise reconciliation is required. A known-settled legacy ID is reset, never
resumed. Failed/ambiguous legacy receipts are not settlement evidence.

Running, uncertain or cleanup-failed records block all subsequent mission phases,
including after snapshot loss, restart or a manually requeued mission state.
No abrupt-controller-death recovery or automatic reconciliation is implemented.

## Receipts and limits

Success uses `agent.receipt`; failure uses `mission.attempt.finished`. Both bind
role, attempt and effective policy digest (null on pre-profile refusal). Provider
failure messages are not copied into controller failure receipts. Typed policy,
isolation and cleanup causes remain durable blockers.

The shared owned adapter now explicitly reports `metadata.ownedRunSettled`: its
existing process wrapper has completed owned-run cleanup, or failed with
CLEANUP_FAILED. This is **not** proof of whole-tree containment. The controller
requires this signal with the matching profile before treating an invoked run
as settled; a TIMEOUT label alone cannot permit replacement. A settled timeout
can follow the existing bounded execution/replacement path while keeping
`externalEffects: UNKNOWN`. Knowledge of process termination is distinct from
knowledge of effects. Unproved cleanup never takes that path.

Output/unterminated-JSONL limits, cancellation, timeout/cleanup implementation,
subscription refusal, routing, journal and accepted admission/context/result/
audit guards are preserved. Test-only legacy adapters receive explicit fixtures
in `tests/fixtures/controller-options.js`; they are not production policy defaults
or process-level acceptance. The new Linux proof uses the actual controller,
shared adapter, pinned fixture, bubblewrap filesystem and durable journal, and
stops before integration/candidate/release.

Host sandbox and hardware/live acceptance remain NOT_TESTED. The six-process
incident is untouched. One bounded GPT-5.5 Medium read-only lifecycle review was
used; Astra retained implementation and integration. Its legacy receipt finding
was repaired; its settlement concern was addressed with an explicit owned-run
signal and an unproved-timeout regression, without conflating effect uncertainty
with a live unresolved process.
